CORE Game Developer's Toolkit

CORE is a full game framework, not a utility library. It owns application boot, DI, the update loop, resource loading, configs, saves and UI. Code that ignores its conventions compiles and then silently does nothing (view never updates, config never loads, resource enum never exists).

Where it lives: Assets/COREToolkit/

  • Scripts/Shared/ — runtime framework (asmdef Game_Shared_AD, namespace CORE.Shared.*)
  • Scripts/Editor/ — editor tools (Game_Editor_AD, Game_SharedEditor_AD)
  • EditorKit/ — the CORE Editor Kit (EditorKit_AD, namespace CORE.EditorKit): the UI Toolkit base of every editor window — theme, glyphs, components, texts, KitModule, KitWindow. Portable: references nothing of CORE
  • Scripts/Shared/CodeGenerated/ — generated *.cg.cs, never hand-edit
  • Examples/Scripts/ — the canonical usage examples; read these before inventing a pattern
  • ModTool/, ThirdParty/ (Zenject, UniTask, Steamworks.NET; GameToolkit-Localization is legacy, removed in 1.4.0)
  • Resources/Configs/ — .json configs loaded at boot

This skill ships inside the CORE package (Assets/COREToolkit/AI/Skills/) and is installed into .claude/skills/ by Tools/CORE/Settings → AI → Install skills. Do not edit the installed copy — CORE overwrites it on update; put project-specific rules into the project's own CLAUDE.md.

Covered version is v1.3.93 (bundles read from Assets/StreamingAssets/Bundles/<Target>; has any number of PlayerResourceSettings assets merged together; palette-hash colors — ColorLibrary.TryGetColor(hash), _colorHash on graphic components; DynamicConfigSingle, SceneLoader.LoadDelay, ActivatePreloadedScene, CSV-table localization with LocKey (since v1.2), CachedValue, GlobalVisual.TryGetVisual; the in-game console is CORE's own (CORE.Console, since v1.2); input is built on Unity Input System — GameInputActions + IInputProvider, see references/systems.md).

Every part of CORE (Base, UI, Configs, Resources, Localization, Audio, Input, Console, Mods, Steam, Editor) has a major.minor.patch version of its own, shown as tiles in Tools/CORE/Welcome. Assets/COREToolkit/CHANGELOG.md starts every bullet with its part (- {audio} …) and every version with what to do once after updating; a part's major means a migration or a broken API (run Setup Wizard → Migrations), minor a feature, patch fixes only.

Non-negotiable rules

  1. Do not modify Assets/COREToolkit/Scripts/ unless the user explicitly asks to patch the framework. It is a purchased asset and gets overwritten on update. Game code goes in its own folder/asmdef that references Game_Shared_AD. The one known unavoidable exception is adding members to SceneLoader.Scenes — see references/setup.md.
  2. Never hand-edit *.cg.cs. They are regenerated by Tools/CORE/Game Window → Resources → Generate. The same goes for Scripts/Shared/Inputs/GameInputActions.cs — the Input System package generates it from Resources/InputSystem_Actions.inputactions.
  3. Custom assets go in PlayerResources, not in CORE's own ResourceSettings — that is what keeps CORE updatable. (Create/CORE/PlayerResources in any Resources/ folder; any name, one asset per game or package — CORE loads and merges them all.)
  4. After adding any resource, color, localization key or input key, code generation must be re-run before the corresponding enum member exists. If a generated enum member you need is missing, say so — do not invent the enum value.
  5. Every subscription needs its matching unsubscription. CORE is event-driven throughout (EventClick, InputSystem.RegisterAction / RegisterProvider, GlobalUpdater.SubscribeUpdate, SaveComponentsManager.Add). The pairing points are Setup()/Sleep() in a View, or OnEnable/OnDisable (Awake/OnDestroy) in a MonoBehaviour.
  6. The docs site lags the code. When mynameisvoo.github.io/COREDocumentation disagrees with Assets/COREToolkit/Scripts, the local source wins. Known drift is listed below.
  7. Do not run builds or play mode to "verify" unless the user asks. Verify by reading source and matching existing patterns, and say plainly what was not runtime-tested.
  8. Instantiate through the DI container. Every new object, element or prefab goes through DiContainerRef.Container.* — never new for a type with injected members, never Object.Instantiate / GameObject.Instantiate for a prefab. Raw instantiation skips injection and every [Zenject.Inject] field on the new object stays silently null. See the table in references/vvm.md → "Creating things through the container". Legitimate exceptions: pure data (configs, DTOs, structs, ViewData), copying a Unity asset (Instantiate(material)), and prefabs obtained from a generated Load* resource method — those already call InstantiatePrefab internally.
  9. Visual fields are non-null by contract. A serialized reference on a Visual is wired in the prefab, so the View never null-checks it — no if (Visual.X == null), no Visual.X?., no != null ternary. Mark the field [CanBeNull] (JetBrains.Annotations, bundled in UnityEngine.CoreModule) if and only if it is genuinely optional; that is what licenses a check. See references/vvm.md → "Visual fields are a non-null contract".

// --- A screen (see references/vvm.md for the full lifecycle)

{
public CustomButton Button;
private MyView _view;

_view = DiContainerRef.Container.Instantiate<MyView>(new object[] { this });

}
}

var rc = ResourcesPlayerGenerated.LoadGameObjectExamples(

Before you finish

  • No null-check on a Visual field that is not [CanBeNull] (rule 9).
  • Does every += have a matching -= on the teardown path?
  • Does the new type live outside Assets/COREToolkit/Scripts/?
  • Does any new resource/color/localization/input key require the user to run Tools/CORE/Game Window → Resources → Generate? Say so explicitly.
