Model, Save System, FileManager

Namespaces: CORE.Shared.Data, CORE.Shared.Data.User, CORE.Shared.Save, CORE.Shared.Save.Data, CORE.Shared.Utils (FileManager, the save interfaces).

There are two separate stores, and mixing them up is the usual bug:

Model.User (UserData) Model.LocationData + the save slot
Scope the player/profile, one per install one playthrough / save slot
Written automatically on application quit (GameApplication.OnApplicationQuit) and via TrySave() / MarkModified() explicitly via SaveSystem.Save(...) / SaveFiles(...) / SaveAuto(...)
On disk {persistentDataPath}/Saves/UserData.json; Saves/UserDataEditor.json in the editor and a development build (UserData.FileName) {persistentDataPath}/Saves/Save_<n>/ and /AutoSaves/Save_<n>_<k>/
Encryption GlobalConfig.Config.EncryptUserData (release builds only) —

The player's settings (Settings) are a third file, {persistentDataPath}/Settings.json — see systems.md.

Model

public static class Model
{
public readonly static UserData User; // loaded in the static ctor
public readonly static LocationData LocationData;
public static void Init(); // called by GameApplication
}

Model is static and available everywhere — but only after GameApplication.OnInitted: its static constructor reads Settings, and a failed static constructor leaves Model unusable for the whole session. LocationData is the cross-scene blackboard.

UserData

Version, FileName, CustomData (UserCustomData), Mods, RequiredEnabledAtStartMods, plus Clone, MarkModified, TrySave, TryLoad, SetCustomData, and the mod bookkeeping (OnModEnableChanged, OnModRemoved, RemoveMods, AddModToReboot, IsModInRequiredToRebootList).

Attach game-wide profile data by subclassing UserCustomData (override Validate()) and calling Model.User.SetCustomData(new MyUserData()). Call Model.User.MarkModified() after changes so the quit-time save actually writes.

LocationData

Id, GameState (New / Continue), CreationTime, CustomData (LocationCustomData), SaveData (the main file last loaded or saved), Path/FileName, IsValidData, a seeded System.Random Rnd, and the id allocator of the slot (IDs, FreeIDs, GetNewID(), AddID(long) — returns a deleted object's id, O(1)). The id counter is one per slot, shared by every file of it, and lives in the main file.

InitNew(customData) / Init(id, gameState, creationTime[, customData]) / SetData(saveData[, customData]).

House pattern for typed access (from Examples/Scripts/SaveGameDataExample.cs):

public class MySaveData : LocationCustomData { public int SaveVersion; }
public static class MySaveDataExtension
{
public static MySaveData GetSaveCustomData(this LocationData thiz) => thiz.CustomData as MySaveData;
}
// after GameApplication.OnInitted — Model must not be touched earlier
if (Model.LocationData.GetSaveCustomData() == null)
Model.LocationData.InitNew(new MySaveData());

The slot

A slot is a folder. Its files:

File Class Holds
SaveData_<Id>.json (autosave: SaveData_<Id>_<k>.json) — the main file SaveData id counter (IDs, FreeIDs), CustomData, AdditionalFiles (names of the slot's files), the data of main-file components
<name>.json, any number (Location_3.json) — additional files SaveFileData the data of the components whose SaveFile is <name>

Both derive from SaveFileBase: Data (list of SaveGameBaseComponentData), GetData(Type) (the first of the type), GetDatas(Type), GetData<T>(), GetDatas<T>(), GetData(saveKey), AddData(components), Path, FileName, FullPath, IsFileExist, GameVersion, GameBuildVersion, Version (bumped by every save), FormatVersion. SaveData adds IsValid, MarkModified(), TrySave(), TryLoad(), DeleteSave() (deletes the whole folder).

A slot with only the main file is what CORE always had; a game that never names an additional file sees no change.

Saving a component

Anything that wants to be part of a save implements ISaveGameBaseComponent and registers with SaveComponentsManager. Two kinds:

ISaveGameBaseComponent (plain) ISaveGameFileComponent
File the main file SaveFile — an additional file by name, null/empty for the main file
Found on load by your code, in SaveSystem.OnLoadingComplete (saveData.GetData(typeof(X.Data))) SaveKey, unique per file
LoadData called by you SaveSystem, in LoadPriority order (lower first, ties in registration order)
public class HealthSave : ISaveGameFileComponent
{
public class Data : SaveGameBaseComponentData // one nested data class per component
{
public float Health;
}
private readonly Character _character;
[Zenject.Inject] protected SaveComponentsManager _saveComponentsManager;
public string SaveKey => "health";
public string SaveFile => null; // main file
public int LoadPriority => 0;
public string ProgressMessage => "Saving health..."; // shown by ProgressVisual
public HealthSave(Character character)
{
_character = character;
}
public void Init() => _saveComponentsManager.Add(this);
public void Destroy() => _saveComponentsManager.Remove(this);
public SaveGameBaseComponentData CollectData()
{
return new Data { Health = _character.Health };
}
public void LoadData(SaveGameBaseComponentData savedData)
{
if (savedData is not Data data)
return;
_character.Health = data.Health;
}
}
// construction goes through DI so [Inject] fields are filled:
var save = DiContainerRef.Container.Instantiate<HealthSave>(new object[] { character });
save.Init();

Optional interfaces, on a component or on an entity of a collection:

  • ISaveGameReferences.ResolveReferences() — the second phase of a load, after every component of the load got its data: find other objects by id here, never in LoadData.
  • ISaveGameCallbacks.OnBeforeSave() (before collecting) / OnAfterLoad() (after references).

Views can be save components directly — derive from ViewSavedBase<TVisual, TDataSave> (Visual must derive from VisualSaved). It injects _saveComponentsManager and does Add/Remove inside Subscribe()/Unsubscribe(); you implement ProgressMessage, CollectData(), LoadData(...) and UniTask Init(). It is a plain component — load it from OnLoadingComplete.

Entities: SaveGameCollection

Many things of one kind (buildings, units, items) save themselves: each implements ISaveGameComponent<TData> (long Id, Init(), TData CollectData(), LoadData(TData)), its data derives from SaveGameComponentData (Id, Clone). A SaveGameCollection<TComponent, TData> gathers them into one SaveGameCollectionData<TData> (List<TData> Items) and is the one ISaveGameFileComponent you register.

var buildings = new SaveGameCollection<Building, Building.Data>(
saveKey: "buildings", saveFile: "Location_3", loadPriority: 0,
factory: data => DiContainerRef.Container.Instantiate<Building>()); // creates what the save has and the scene not
_saveComponentsManager.Add(buildings);
var building = DiContainerRef.Container.Instantiate<Building>();
building.Id = Model.LocationData.GetNewID();
buildings.Register(building); // Unregister on destroy, and Model.LocationData.AddID(building.Id)
  • CollectData asks every entity and stamps its Id.
  • LoadData gives each data to the registered entity with that Id; a data with no entity goes to the factory (or override protected virtual TComponent Create(TData)), the collection sets the id, registers it and calls LoadData. An entity the data does not have goes to protected virtual OnMissing(TComponent) (default: kept).
  • ResolveReferences / OnBeforeSave / OnAfterLoad are forwarded to every entity that implements the interface.
  • Items, Count, TryGet(id, out c), Get(id), Clear().
  • Load what others reference with a lower priority — or just resolve in ResolveReferences, which runs after all.

SaveSystem

Injected ([Zenject.Inject] private SaveSystem _saveSystem;), bound in ProjectInstaller.

public event Action<SaveData> OnLoadingComplete;
public event Action<SaveFileData> OnFileLoadingComplete;
public event Action OnSavingComplete;
public bool DebugLoadByPress; // editor-only load hotkey, off by default
public bool IsActive { get; } // a save or load is running; another call is refused
public static string SlotFolder; // where the current slot's files are read from
await _saveSystem.Save(onSavingComplete, autoSaveId: null); // main file + files of the registered components
await _saveSystem.SaveFiles(new[] { "Location_3" }, includeMain: true, onSavingComplete);
await _saveSystem.SaveAuto(onSavingComplete); // next autosave slot by rotation
await _saveSystem.Load(null, onLoadingComplete); // Task<SaveData>; null = read the main file from disk
await _saveSystem.LoadFile("Location_3"); // UniTask<SaveFileData>; null if never saved
_saveSystem.Subscribe(component); // same role as SaveComponentsManager.Add
_saveSystem.Unsubscribe(component);
SaveSystem.GetSaveDatas(directory); // static, enumerate slots -> List<SavedFileData>
SaveSystem.GetSaveDatas(listOfDirectories); // an unreadable slot is logged and skipped
  • Save pauses the game (and restores the pause it found), calls OnBeforeSave, collects on the main thread, then writes the main file first and the additional files after. Only the files of the registered components are written — a location that is not loaded keeps its file as it is. SaveFiles(files, includeMain: false) still writes the main file (the id counter must not fall behind), with the component data it last saved or loaded.
  • Saving into another folder than the slot was loaded from (an autosave, or a save after loading an autosave) copies the additional files that were not written along, so every folder is a whole slot. Only the files listed in SaveData.AdditionalFiles are copied; nothing is ever deleted but by DeleteSave, and other files a game keeps in the slot folder are not touched.
  • Load reads the main file and the additional files of the registered ISaveGameFileComponents, sets Model.LocationData (id counter, CustomData) from the main file — also when a SaveData is passed in — then gives data out: LoadData by priority → ResolveReferences → OnAfterLoad, then OnLoadingComplete. An exception in one component is logged and the rest still loads. There is no fixed delay any more.
  • LoadFile does the same for one additional file and the components that write to it — typically after a location scene is loaded and its components registered. null (nothing touched) when the file was never saved: initialize the location fresh.
  • SaveAuto picks a missing slot of 0..GlobalConfig.MaxAutoSaveSlots-1, else the oldest; 0 disables it. Save(cb, autoSaveId) still writes a given slot.

Files: atomic, async, versioned

SaveFileIO reads and writes every slot file:

  • Atomic: written to <file>.tmp, then it replaces the file. A crash leaves the previous file whole. Files of one save are not one transaction — the main file goes first, so a crash can lose a location's latest state but never hand out an id twice.
  • Thread pool: SaveFileIO.UseThreadPool = true (off by default, ignored on WebGL) serializes, writes and reads off the main thread — for large saves. CollectData and LoadData stay on the main thread; turn it on only if no data class touches the Unity API in a constructor, field initializer, property or converter, and holds no Unity object. SaveFileIO.Formatting = Formatting.None for large saves.
  • Type names: TypeNameHandling.Auto — $type only where the declared type differs (list items, a LocationCustomData subclass). SaveTypes.Register<T>("unit", "Old.Namespace.UnitData") writes the type by an alias and reads it from its old full names, so renaming or moving a class keeps old saves readable (generic arguments included). Files written by older CORE ($type everywhere) still read. Register at boot.
  • Migrations:
    • File: SaveMigrations.Register(toVersion, (JObject json, string fileName) => …). Every file stores the FormatVersion it was written with; an older one runs the migrations above it, in order, on the raw json, before it becomes objects — rename and move fields here. Registering raises SaveMigrations.CurrentVersion.
    • Data: SaveGameBaseComponentData.DataVersion; override CurrentDataVersion and protected override void Migrate(int fromVersion). Runs after reading, for collection items too (NestedData). Fields that no longer exist are gone by then — use a file migration or [JsonExtensionData].
  • IsValid / MinSupportedSaveGameBuildVersion still reject saves of too old a build.

Design the game so it works in two states: fresh (GameState.New, InitNew) and loaded (GameState.Continue), and never assume a save exists.

Recipe: a world slot with a file per location

The world is the slot; each location has its own file; buildings and units save themselves. Runnable version: Examples/Scripts/SaveSlotFilesExample.cs, console command example.save_slot_files.

// World-level data: the main file
public class WorldSave : ISaveGameFileComponent
{
public class Data : SaveGameBaseComponentData { public int Day; public int CurrentLocation; }
public string SaveKey => "world";
public string SaveFile => null;
public int LoadPriority => 0;
public string ProgressMessage => "World...";
// CollectData / LoadData as usual
}
// One per loaded location scene
public class LocationSave
{
public readonly SaveGameCollection<Building, Building.Data> Buildings;
public readonly SaveGameCollection<Unit, Unit.Data> Units;
[Zenject.Inject] private SaveComponentsManager _saveComponentsManager;
public LocationSave(int location) // created through DiContainerRef.Container.Instantiate<LocationSave>(new object[] { n })
{
var file = $"Location_{location}";
Buildings = new SaveGameCollection<Building, Building.Data>("buildings", file, 0,
_ => DiContainerRef.Container.Instantiate<Building>());
Units = new SaveGameCollection<Unit, Unit.Data>("units", file, 10,
_ => DiContainerRef.Container.Instantiate<Unit>(new object[] { this }));
}
public void Register() { _saveComponentsManager.Add(Buildings); _saveComponentsManager.Add(Units); }
public void Unregister() { _saveComponentsManager.Remove(Buildings); _saveComponentsManager.Remove(Units); }
}
public class Unit : ISaveGameComponent<Unit.Data>, ISaveGameReferences
{
public class Data : SaveGameComponentData { public long HomeId; }
private readonly LocationSave _location;
private long _homeId;
public Unit(LocationSave location) => _location = location;
public long Id { get; set; }
public Building Home;
public void Init() { }
public Data CollectData() => new Data { HomeId = Home?.Id ?? -1 };
public void LoadData(Data data) => _homeId = data.HomeId; // no lookups here
public void ResolveReferences() => Home = _location.Buildings.Get(_homeId);
}
// Starting the game: await _saveSystem.Load(null, null); // main file + registered location files
// Entering a location: locationSave.Register(); await _saveSystem.LoadFile($"Location_{n}"); // null → new location
// Saving: await _saveSystem.Save(null); // main + the loaded location only; other locations untouched
// Leaving a location: await _saveSystem.Save(null); locationSave.Unregister();

Gotchas

  • Visual.OnDestroy skips View teardown when GameApplication.AppQuit is set, so a save that relies on View.Destroy() will not run at quit. Hook GameApplication.OnAppQuit instead.
  • A component that never calls _saveComponentsManager.Add(this) is silently absent from the save — and for an additional file, absent means the file is not written at all.
  • LoadData receives SaveGameBaseComponentData; always pattern-match to your nested Data type and return early on mismatch.
  • Remember Remove(this) on destroy or the manager keeps a dead reference.
  • SaveKey must be unique within its file; two components with one key — only the first loads (logged on save).
  • An additional file name is a plain file name: no path, not starting with SaveData_.
  • Save/Load refuse to run while another one is running (IsActive) — await one before starting the next.
