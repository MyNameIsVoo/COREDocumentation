Mod support (ModTool)

Source: Assets/COREToolkit/ModTool/ — a heavily reworked ModTool. Namespaces: CORE.ModTool (runtime), CORE.ModTool.Shared, CORE.ModTool.Editor.Exporting, CORE.ModTool.Tool.Mod (startup attributes).

A mod is an Assembly Definition compiled to a DLL plus asset bundles, dropped into <GameRoot>/Mods/<ModName>/. The game side never references the mod; the mod references the game's public API.

Mod (Resource<Mod>): Info (ModInfo), ContentType, IsValid, IsEnabled, CanLoad, ConflictingMods / UpdateConflicts(...) / ConflictingModsLoaded() / ConflictingModsEnabled(), Scenes, Prefabs, Assets, Sprites, Texts, Audio, LocalizedTexts (legacy), GetAsset<T>(name), GetAssets<T>(), GetAssetAsync<T>(name), GetTextAsset(name), GetAudioClip(name), GetAudioClips(), GetNewComponent<T>(name), GetAssetComponents<T>(), GetSceneComponents<T>(), GetAssetBundle(type, assetName).

ModScene: Scene, SetActive(), GetComponentInScene<T>(), GetComponentsInScene<T>().

Enabled/disabled state and "needs restart" bookkeeping live on Model.User (Mods, RequiredEnabledAtStartMods, OnModEnableChanged, OnModRemoved, RemoveMods, AddModToReboot, IsModInRequiredToRebootList). GlobalConfig.Config.ResfreshModsCooldownTime throttles rescans.

Mods hook into the rest of CORE through the same public seams the game uses: ConfigSystem.InsertConfigs (extra config files), localization tables (every .csv in a mod's bundle is registered by ModLocalization through LocalizationManager.RegisterTable with priority RuntimeTablePriority + LoadOrder and overrides the game's keys; unregistered on unload), the audio catalog (the clips of a mod's audio bundle are registered by name through AudioCatalog.Register with priority AudioCatalog.RuntimePriority + LoadOrder, so a mod clip named like a game clip replaces it; unregistered on unload), AssetBundlesManager.OnTryLoadAsset, and GlobalVisual's IModSupportVisual surface:

_globalVisual.AddModVisual<TVisual>(visual);
_globalVisual.RemoveModVisual<TVisual>(visual);
_globalVisual.RemoveModTypeVisuals<TVisual>(modSupportVisual);
_globalVisual.UpdateModVisualsList();
_globalVisual.ModScreenContent; // parent transform for mod visuals

Implement IModSupportVisual on one of your own screens to give mods a docking point; without one, mod visuals attach to GlobalVisual. ConfigVisual<T> exists so a mod can name a visual/resource in a config by the same rules the game uses.

Mod entry point (the modder's side)

using CORE.ModTool;
using CORE.ModTool.Tool.Mod;
using UnityEngine;
namespace MyFirstMod
{
public class Boot : ModHandler
{
private static Boot _instance;
[ModOnLoaded]
public static void ModOnLoaded(Mod mod)
{
if (mod == null)
return;
_instance = Create<Boot>(mod);
}
[ModOnUnloaded]
public static void ModOnUnloaded(Mod mod)
{
if (_instance != null && _instance.gameObject != null)
GameObject.Destroy(_instance.gameObject);
_instance = null;
}
}
}

ModHandler is a MonoBehaviour with Mod, the usual Unity callbacks, SetData(Mod) and the static factory Create<T>(mod). [ModOnLoaded] / [ModOnUnloaded] mark the static entry points; free everything in the unload path.

Mod folder layout on disk:

Game/Mods/MyFirstMod/
├── Resources/Content/ # icons, images
├── Windows/ # asset bundles
├── MyFirstMod.json # manifest
└── MyFirstMod_AD.dll # logic

Manifest fields: IsEnabled, Data { Names, Authors, Descriptions, Version, Platforms, Content, RequiredReboot, LoadOrder, OutputDirectory, Assets, ScriptsDirectory, Images, IconPath, UnityVersion }. Platforms is ModPlatform, Content is the ModContent flags enum (HazFlag, GetFilter extensions).

Mod texts are LocaleText[] { Language, Value }: Data.GetName(), GetAuthor(), GetDescription(), Images[i].GetDescription() pick the current language with fallbacks. The pre-1.2 Name / Author / Description (LocaleItem<string>[]) and NameLocalized & co. are obsolete (removed in 1.4.0): old manifests and export settings are converted on load, and saving writes both formats so games on an older CORE still read the mod. A mod localizes its own content with .csv tables and <Group>/<language>/<Key>.* asset folders in its bundle (same format as the game's).

Exporting the toolkit for modders (developer side)

  1. Tools/CORE/Game Window → Mod Tool → Create Exporter.
  2. Copy the produced CoreModTool folder into an empty Unity project of the same engine version and settings as the game, under Assets/.
  3. Console errors right after export are expected; they clear once assemblies recompile.

ModToolSettings (singleton ScriptableObject) holds what is exported: State (ModToolStates, keep Debug while developing so the tool is not shipped with every build), Version, SupportedPlatforms, SupportedContent, LogLevel, SharedDLLs (from Library/ScriptAssemblies/), SharedSettings, SharedAssets, SharedPackages, OutputDirectory.

Restrictions (CORE.ModTool.Shared.Verification.Restriction + CodeSettings) are enforced at verify time: inheritance, member, type and namespace restrictions. Use them to keep mods away from unsafe APIs.

The modder's export window

Tools/ModTool/Export Mod:

  • Prepare — generates Boot.cs and {ModName}_AD.asmdef in the mod project.
  • Verify — checks restrictions; export is blocked on failure.
  • Export Mod — builds and writes to the output directory.
  • Mod Preset / Save / Load — several mods can live in one project.

Mods cannot be tested inside the mod project — export first, then drop into the game's Mods folder. ModManager (the docs call it ModsManager) picks the folder up and lists it. RequiredReboot forces a restart when the mod is toggled.

Requirements on the mod project: same Unity version, com.unity.nuget.newtonsoft-json installed, the two preset text files moved from Assets/Resources into <Project>/Library/.

What to do in this repo

Mods are a shipping-time concern; day to day the relevant part is not breaking the seams: keep the game's mod-facing API public and stable, keep IModSupportVisual roots intact, and prefer EnumData<T> / ConfigVisual<T> in configs so mods can address resources by string.
