Project setup: what a CORE project needs before any game code runs

Read this when the project is new, a scene "does nothing", DiContainerRef.Container is null, or [Zenject.Inject] fields stay null. Everything below is what the shipped ExamplesScene already has; a new scene must replicate it.

Player / build settings

Setting Value
Scripting Backend Mono
Api Compatibility Level .NET Standard 2.1 or higher
Managed Stripping Level Disabled
Active Input Handling Both (CORE code itself uses only Unity Input System)
Build Settings → Scenes all scenes CORE loads, named exactly as SceneLoader.Scenes — SceneLoader loads by scene.ToString(), see below

Required packages: com.unity.nuget.newtonsoft-json, TextMeshPro (+ TMP Essential Resources imported), Input System 1.6.3+. Zenject, UniTask, Steamworks.NET (and, until 1.4.0, the legacy GameToolkit-Localization) are vendored under Assets/COREToolkit/ThirdParty/ — do not install them again from the Package Manager or the Asset Store, you will get duplicate-type errors.

Render pipeline: Game_Shared_AD.asmdef references Unity.RenderPipelines.Universal.Runtime and Unity.RenderPipelines.Core.Runtime (missing ones are ignored without URP) and declares ENABLED_URP / ENABLED_HDRP as asmdef version defines — they exist only inside Game_Shared_AD and only while the package is installed. They are not Player Settings defines: your own assemblies do not see them; give an assembly of yours its own versionDefines entry if it needs one. Code that touches UniversalRenderPipelineAsset must sit behind #if ENABLED_URP (QualityPresetSetting, UnityGraphics do). Nothing has to be configured by hand. If the project shows CS0234/CS0246 on UnityEngine.Rendering.Universal, MsaaQuality or ScriptableRendererData in Game_Shared_AD, the asmdef lost those entries or Player Settings still carry an old ENABLED_URP without URP installed: Setup Wizard → Render pipeline → Fix (also offered in a dialog on the compile error) restores both. The check lives in its own assembly Game_PipelineEditor_AD (Scripts/Editor/Pipeline/), referencing only the Editor Kit.

The project-wide prefab: Resources/ProjectContext.prefab

Zenject loads Resources/ProjectContext.prefab automatically before the first scene. It is the only place CORE's singletons live; there is no "CORE manager" object to drop into a scene. Components on it:

Component Role
ProjectContext (Zenject) creates the project container, runs the installers listed on it
ProjectInstaller binds the fields below with BindInterfacesAndSelfTo<T>().FromInstance(...), plus InputSystem .FromNew()
GameApplication boot sequence (see vvm.md → "Boot sequence"), HasBeenInitted, OnInitted, OnAppQuit
GlobalUpdater, GlobalVisual, AudioSystem, SaveSystem, SaveComponentsManager, CustomCursor, Dispatcher, UIScaler the injectable singletons — these are the fields of ProjectInstaller
SteamManager, SteamLoader Steam init on standalone; in the editor only with Enable Steam on, in a build unless CORE_DISABLE_STEAM is defined (SteamManager.IsEnabled)
LocalizationManager (static) the language is applied by Settings.Apply() (GameSettingsData.Language, Steam language on first start) before the bundles load; tables are read on first use and again on AssetBundlesManager.OnLoaded

Consequences:

  • A scene never needs its own copy of any of these. If you see two GlobalVisuals, one is a mistake.
  • GlobalVisual.Show(name) works only for visuals listed in the GlobalVisual component's _visuals array on this prefab — register new named screens there.
  • The prefab has no Canvas. The UI root is yours: the example loads UI_ExampleUICanvasPrefab (a Canvas prefab with a CanvasReference component) from Boot, and CanvasReference.Instance then points at it. Generated LoadVisualScreen(enumData, root) parents the screen under whatever root you pass.
  • To add your own project-wide system: put it into your PlayerProjectContext prefab (next section), or bind from a scene installer (below) if it is scene-scoped.

Never edit ProjectContext.prefab in Assets/COREToolkit/Resources/ — an update overwrites it with everything added to it — and never make a second Resources/ProjectContext prefab (a copy or a variant): Zenject refuses to start with two (Resources.LoadAll asserts at most one).

The game's project-wide prefab: Resources/PlayerProjectContext.prefab

Since v1.2 the game's own project-wide services live in a prefab of their own, never in CORE's. Create it with Assets/Create/CORE/Player Project Context (or the Setup Wizard fix) — it lands at Assets/Resources/PlayerProjectContext.prefab; any Resources folder works, the file must be named PlayerProjectContext (PlayerProjectContext.ResourcePath), and only one may exist.

How it is attached (PlayerProjectContextLoader, Scripts/Shared/DI/): on Zenject's ProjectContext.PreInstall CORE instantiates the prefab as a child of its own context root — still inactive, before the container collects its injectables — and appends the game's installers after CORE's. So:

  • Every MonoBehaviour in the prefab gets [Inject] like CORE's services, and its Awake / Start run after injection. It is DontDestroyOnLoad with the context.
  • The root component PlayerProjectContext (a MonoInstaller) has three lists:
    • Bindings (Component[]) — each is bound with BindInterfacesAndSelfTo(component.GetType()).FromInstance(component).AsSingle(); enough for most services, no installer to write.
    • Installers (MonoInstaller[]) — must be components inside this prefab; one outside it is skipped with an error.
    • Scriptable Object Installers — installer assets. All of them run after CORE's ProjectInstaller, so they can resolve CORE's services. Binding a contract CORE already binds makes Zenject fail on resolve — do not rebind CORE's services.
  • Without the prefab nothing happens; CORE works as before.

Setup Wizard → Optional → ProjectContext warns while CORE's ProjectContext.prefab holds a script that is not CORE's or a Unity package's (or a missing script), offers to create PlayerProjectContext, and fails on a second Resources/ProjectContext prefab. Moving the components is manual: recreate them in PlayerProjectContext, re-link their references, remove them from CORE's prefab.

A scene that works

Minimum hierarchy (this is Examples/ExamplesScene.unity):

SceneContext (Zenject.SceneContext)
├── DiContainerInstaller (CORE.Shared.DI) — publishes the container to DiContainerRef.Container
└── BootInstallerDI (your MonoInstaller, optional) — binds scene-level objects
Boot (your BootBase subclass)

Both installers go into SceneContext.Installers. DiContainerInstaller must be present in every scene that constructs Views — without it DiContainerRef.Container is null and every Visual.Create throws. Zenject also requires the SceneContext for [Zenject.Inject] fields on scene MonoBehaviours to be filled.

The scene entry point derives from BootBase (Scripts/Shared/BootBase.cs), which injects _audioSystem and exposes virtual Awake/Start/OnDestroy. Wait for GameApplication:

public class Boot : BootBase
{
private ResourceComponent _screenRC;
protected override void Awake()
{
base.Awake();
GameApplication.OnInitted += OnInitted;
if (GameApplication.HasBeenInitted) // true when this is not the first scene
OnInitted();
}
protected override void OnDestroy()
{
base.OnDestroy();
_screenRC?.Unload();
}
private void OnInitted()
{
GameApplication.OnInitted -= OnInitted;
_screenRC = ResourcesPlayerGenerated.LoadGameObjectExamplesScreens(
new EnumData<ResourcesPlayerGenerated.ExamplesScreensScreens>(
ResourcesPlayerGenerated.ExamplesScreensScreens.UI_ExampleUICanvasPrefab, null), null);
}
}

Before OnInitted configs, resources, Model, Settings and Steam are not guaranteed to exist. Examples/Scripts/Boot.cs + BootInstallerDI.cs are the reference pair.

Scenes and SceneLoader.Scenes

SceneLoader.Scenes is a hand-written enum in the framework (Scripts/Shared/ScenesLoader/SceneLoader.cs): Boot, Meta, Loading, Location, None. SceneLoader.Load calls SceneManager.LoadSceneAsync(scene.ToString(), mode), and ScenesExtensions.ToSceneType(scene.name) does Enum.Parse on unload. Therefore:

  • Scene assets must be named exactly Boot, Meta, Loading, Location (case-insensitive on parse, exact on load) and be in Build Settings.
  • The package ships only ExamplesScene; you create the game scenes yourself.
  • A scene with any other name cannot be loaded through SceneLoader, and unloading it fires OnSceneUnloadedEvent with an Enum.Parse exception. Adding your own scene names means editing the enum in the framework — the one case where touching Assets/COREToolkit/Scripts/ is unavoidable. Keep the five built-in members, append yours, and re-apply after a CORE update. Prefer modelling levels as additive sub-scenes loaded with plain SceneManager under a SceneLoader-managed Location.

CurrentScene starts as Boot — the first scene in Build Settings is assumed to be the boot scene. Load is a no-op when scene == CurrentScene unless forceLoad: true.

LoaderCallback (ScenesLoader/LoaderCallback.cs) is a MonoBehaviour for a loading screen: on its first Update it calls SceneLoader.LoaderCallback(), which runs the deferred additive load Load registered for the target scene when the previous scene was not Boot. Put it on an object in the Loading scene and read SceneLoader.GetLoadingProgress() for the bar.

Checklist for a new scene

  1. SceneContext with DiContainerInstaller (+ your MonoInstaller) in its installers list.
  2. A BootBase subclass that waits for GameApplication.OnInitted / HasBeenInitted.
  3. Scene named after a SceneLoader.Scenes member and added to Build Settings.
  4. A Canvas with CanvasReference (scene object or a prefab loaded from Boot), and screens as prefabs declared in PlayerResourceSettings, loaded through the generated Load* methods and unloaded in OnDestroy. Visuals placed directly in the scene also work — Visual.Awake registers them — but they skip the resource/bundle pipeline.
  5. New named screens added to GlobalVisual._visuals on the project prefab and VisualNames regenerated.
