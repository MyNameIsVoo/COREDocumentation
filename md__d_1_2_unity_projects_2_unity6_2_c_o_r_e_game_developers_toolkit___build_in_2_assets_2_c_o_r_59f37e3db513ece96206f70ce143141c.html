Resources, Code Generator, Asset Bundles, Colors, Localization

These four systems are one pipeline: you declare assets in a settings ScriptableObject, run code generation, and get strongly-typed enums + load/unload methods that transparently read from Resources, StreamingAssets or Asset Bundles.

Namespaces: CORE.Shared.Utils.Resources, CORE.Shared.Utils.AssetBundles, CORE.Shared.Generated.Resources, CORE.Shared.Colors, CORE.Shared.Localize.

The two settings assets

Asset Create menu Who owns it
ResourceSettings Create/CORE/Resources CORE's own — do not add game assets here
PlayerResourceSettings Create/CORE/PlayerResources yours — any number, any file name, each under a Resources/ folder: CORE loads them all (Resources.LoadAll<PlayerResourceSettings>("") in ResourceSettings.LoadPlayerResources()) and merges them in the order of their asset names

At generation time ResourceSettings.Instance.LoadPlayerResources() re-reads every player asset and merges them into CORE's own, so your entries produce a separate generated class. Keeping them separate is what lets CORE be updated without losing your declarations.

Both hold the same three lists:

  • ResourceDatas — { Type, Paths[] }. Enumerations for things that must stay stable project-wide; the Localize entry lists the folders of the localization tables. Merged by Type.
  • BundleDatas — { Name, Variant, Paths[] }. One asset bundle per entry; everything under Paths is included automatically, no per-asset bundle tagging. Names must be unique.
  • AssetDatas — { Name, Bundle, Paths[], NameRegex, EnumValues[], Type, DirectorySavePath }. This is what produces enums and loaders.
    • Type is ResourceSettings.AssetData.Types: Sprite, Texture2D, VideoClip, Visual, GameObject, AudioClip, ScriptableObject (LocalizedText is obsolete — localization is CSV tables).
    • NameRegex splits an asset file name into up to 3 capture groups (MaxEnumValuesAmount = 3); each group maps to one EnumValues entry. Example: files UI_Player_Bob.png, UI_Enemy_Bill.png with regex Name_(.+?)_(.+?)$ yields a Group enum (Player, Enemy) and a Name enum (Bob, Bill). Leave NameRegex empty to use the whole file name.
    • EnumValues entry = { Name, Enum, ToUpper }. If Enum is set (a fully-qualified existing enum such as UnityEngine.KeyCode) it wins over Name.
    • Name and Bundle must be unique.

Running code generation

Tools/CORE/Game Window → Resources → Generate (editor entry point: CORE.Editor.Utils.CodeGenerator.Generate()).

It regenerates, in order: Localization → Color Library → Input System → Resources, writing *.cg.cs into Assets/COREToolkit/Scripts/Shared/CodeGenerated/ (or DirectorySavePath).

Do not run this yourself unless the user asks (it rewrites many .cg.cs files). When a change requires regeneration, add a step to the user saying so, and do not fabricate enum members that do not yet exist in the .cg.cs files.

Using the generated API

Two static partial classes:

  • ResourcesGenerated — CORE's built-in assets (DefaultSprites, CursourSprites, AudioClips, ScreenPrefabs, ModalPrefabs, InputSizes, ...).
  • ResourcesPlayerGenerated — everything declared in your PlayerResourceSettings assets (a partial class; each AssetData generates its own part).

One asset per owner. A game and every package it installs keep their declarations in a PlayerResourceSettings of their own, inside their own Resources/ folder; deleting the folder takes its resources with it. How the merge works (ResourceSettings):

  • GetBundleDatas() — bundles with the same Name + Variant from several assets become one bundle with the union of their Paths.
  • GetAssetDatas() — an entry equal to one already collected (AssetData.IsEqual: same name, bundle, type, regex, save path and enum values, compared by content) is combined with it: its paths are added. A game puts its clips into CORE's Audio entry this way — a copy of that entry in its PlayerResourceSettings with its own paths — instead of editing the package's ResourceSettings, which an update overwrites.
  • GetUIVisualPaths() — all paths, without duplicates.
  • GetData(key) — CORE's ResourceData combined with every player one of that type.
  • PlayerResourcesDatas lists what was loaded; AddData(asset) appends one more at runtime. The old serialized _playerResourcesData field is gone — nothing to assign in the inspector.

Method naming is Load{Type}{AssetDataName} / Unload{Type}{AssetDataName}, with one parameter per EnumValues entry. Read the actual .cg.cs to get the exact names — they are derived from your data, not fixed.

// Plain asset -> returns the asset, unload by the same key
Sprite icon = ResourcesPlayerGenerated.LoadSpriteExamples(
ResourcesPlayerGenerated.ExamplesSprites.UI_ExampleIcon_0);
ResourcesPlayerGenerated.UnloadSpriteExamples(
ResourcesPlayerGenerated.ExamplesSprites.UI_ExampleIcon_0);
// Prefab/Visual -> instantiates under `root` and returns a ResourceComponent handle
ResourceComponent rc = ResourcesPlayerGenerated.LoadGameObjectExamples(
new EnumData<ResourcesPlayerGenerated.ExamplesGameObjects>(
ResourcesPlayerGenerated.ExamplesGameObjects.UI_ExampleGameObject, null),
rootTransform);
rc.Unload(); // destroys the instance and releases the bundle reference
// Existence checks before loading a mod-supplied / config-supplied name
ResourcesGenerated.HasDefaultSprites("SomeName");
ResourcesGenerated.GetDefaultDefaultSprites("SomeName"); // string -> enum, default if unknown

ResourceComponent is a MonoBehaviour attached to the spawned instance: Data { BundleName, Path }, Type, OnUnload, SetData(...), Unload(). Store the handle and call Unload() on teardown — Examples/Scripts/Boot.cs and LoadUnloadResourcesExample.cs both do this in OnDestroy.

Visual-typed assets get extra helpers: GetVisualScreenPrefab(EnumData<ScreenPrefabs>) returns (GameObject Prefab, string Path), LoadVisualScreen(enumData, root) returns a ResourceComponent, UnloadVisualScreen(component).

Asset bundles at runtime

AssetBundlesManager (static) is what the generated loaders sit on top of; call it directly only for paths CORE cannot generate.

AssetBundlesManager.RequiredLoadingBundles // the Game Window "Load Bundles" toggle
AssetBundlesManager.IsActiveLoadingBundles
AssetBundlesManager.LoadingProgress // Progress: LoadFileProgress / DownloadProgress
AssetBundlesManager.OnLoaded
await AssetBundlesManager.Init(); // called by GameApplication at boot
T asset = AssetBundlesManager.LoadAsset<T>(bundleName, path);
AssetBundlesManager.UnloadAsset<T>(bundleName, path, unloadFromMemory: true);
AssetBundlesManager.LoadBundle(name);
await AssetBundlesManager.LoadBundleAsync(name, onFinished, onError);
AssetBundlesManager.UnloadBundle(name, unloadAssets: true);
AssetBundlesManager.CleanBundlesCache();
AssetBundlesManager.OnTryLoadAsset // hook for mods to supply their own bundle

Where bundles must be (fixed contract): Application.streamingAssetsPath/Bundles/<platform>, i.e. AssetBundlesManager.GetBundlesFolder(platform) → Assets/StreamingAssets/Bundles/StandaloneWindows on Windows (AssetBundlesManager.CurrentPlatform; empty on any other platform — CORE loads bundles only on Windows). File names are the declared bundle names in lower case. Not Assets/StreamingAssets/StandaloneWindows, not the StreamingAssets root, not AssetBundles/ in the project root.

Building bundles: Tools/CORE/Game Window → Asset Bundles (build target, output path, clear folders, Build, Clear Bundle Names/Cache). The default output path (and Reset) is exactly that folder; with another output path turn on Copy to StreamingAssets, which copies into it. The page shows whether the bundles are built there (N of M) and moves bundles found in StreamingAssets/<Target> or the StreamingAssets root with one button. Clear Folders deletes only the output folder and Bundles/<Target>, never the rest of StreamingAssets. There is also Tools/CORE/Asset Bundle Browser.

When Load Bundles is off, resources come from Resources/AssetDatabase; when on, everything is read from built bundles and a missing bundle is a console error. A missing Bundles/<platform> folder is one error naming the expected folder (no bundle is loaded). If a resource "disappears" after enabling bundles, the bundle was not rebuilt.

Color Library

Two kinds of palette asset:

Asset Create menu Role
Resources/ColorLibraryData Create/Colors/Color Library Data CORE's library; only these palettes get ColorEnums members on generation
PlayerColorLibraryData Create/Colors/Player Color Library Data extra palettes of a game or plugin; every asset under any Resources/ folder is registered into ColorLibrary automatically (editor load and game start, PlayerColorLibraryData.Register()) — found by hash only, no enum members

A color is addressed two ways:

  • Enum tag ColorCustomGenerated.ColorEnums.<PALETTE>_<COLOR> — exists only after code generation, and its number differs from project to project. Fine inside one game.
  • Palette hash (PaletteData.ColorData.Hash, a GUID string) — the same in every project. Use it for anything that travels between projects: plugin/package prefabs, shared UI kits.
ColorCustom c = ColorLibrary.GetColor(ColorCustomGenerated.ColorEnums.DEFAULT_DEFAULT);
bool exists = ColorLibrary.HasColor(someEnum);
ColorLibrary.TryGetColor("9f6db18f-...", out var byHash); // NoneColor + false when unknown
ColorLibrary.HasColor("9f6db18f-...");
ColorCustom r = ColorLibrary.GetRandomColor();
c.MainColor; c.AlternativeColor; c.ColorEnum; c.HasColorEnum; c.Hash; c.Name; c.PaletteName;
ColorLibrary.AddPalettes(palettes); // register palettes from code; a palette hash already known is skipped
ColorLibrary.Refresh(); // re-read ColorLibraryData + added palettes
ColorLibrary.Colors; // ColorCustom[] (read-only property)

Rules: palette names unique; color names unique inside a palette; regenerate after any add or rename in ColorLibraryData, otherwise the ColorEnums member does not exist (HasColorEnum is false). A PlayerColorLibraryData palette with the same hash as one in ColorLibraryData is not doubled — moving a palette into the library later is safe. ColorLibraryData.AddData(...) still exists but nothing calls it any more.

ColorCustom has ctor overloads taking an alpha override. UI components take a Color Tag (the enum) or a Color Hash in the inspector rather than a raw Color — see ui.md.

Localization

CORE's own CSV-table localization (since v1.2; GameToolkit-Localization is legacy, see below). Namespace CORE.Shared.Localize, generated keys in CORE.Shared.Generated.Localization.

Tables. .csv files under the paths of the Localize entry of ResourceDatas (declare game tables in PlayerResourceSettings; the folder must also be in a BundleDatas entry). CORE's own tables: Bundles/Localization/Core.csv, Examples/Bundles/Localization/Examples.csv.

Key,Comment,en,ru
Button_Play,Main menu button,Play,Играть
Coins,,"{0:plural:one=# coin|other=# coins}","{0:plural:one=# монета|few=# монеты|many=# монет|other=# монеты}"
  • Key column (a C# identifier, not a keyword — a keyword or digit-led name gets a leading _ in LocKeys; case-insensitive, unique across tables), service columns Comment / Context / Description / Note, every other column is a language code (en, ru, pt-BR, zh-Hans).
  • RFC 4180 CSV, separator , ; or tab detected from the header, UTF-8. Rows whose key starts with # are comments.
  • Lookup chain: current language → parent (pt-BR → pt) → LanguageSettings.FallbackLanguage (Resources/LanguageSettings, default en). A missing key is logged once, shown as #Key# (LanguageSettings.ShowMissingKeys) and listed in LocalizationManager.MissingKeys.

Code generation writes LocalizationKeys.cg.cs: LocKeys.<Table>.<Key> (static readonly LocKey) and LocalizationTablesGenerated.Tables (what the runtime loads). Adding a key or table requires regeneration before LocKeys.<Table>.<Key> exists — say so, do not invent the member.

LocKey key = LocKeys.Core.Button_Apply; // serialized as the key string, never a number
new LocKey("Button_Apply"); // from data / config strings
LocalizationManager.Get(key); // text in the current language
LocalizationManager.TryGet(key, out var text);
LocalizationManager.Get(key, "ru"); // in a given language
LocalizationManager.Format(key, 5, "Bob"); // {0} {1}, {0:N0}
LocalizationManager.Format(key, new Dictionary<string, object> { ["gold"] = 5 }); // {gold}
LocalizationManager.HasKey(key);
LocalizationManager.SetLanguage("ru"); // raises OnLanguageChanged
LocalizationManager.CurrentLanguage; // "ru"
LocalizationManager.AvailableLanguages; // languages present in the tables
LocalizationManager.OnLanguageChanged += Refresh; // also raised when tables change (mods); unsubscribe!
GlobalConfig.Config.HasLanguage("ru"); // languages the game ships (GameLanguages)
Settings.Game.Language = LocalizationManager.CurrentLanguage; // persist the choice
Languages.GetNativeName("ru"); // "Русский" — for a language picker
Languages.FromSteam(steamName); Languages.FromSystemLanguage(Application.systemLanguage);
LocalizationManager.RegisterTable(name, csvText, priority, owner); // runtime tables, override by priority
LocalizationManager.UnregisterTables(owner);
LocalizationManager.PseudoLocalization = true; // accented, longer texts for layout testing
LocalizationManager.Reload();

Plurals: {n:plural:one=…|few=…|many=…|other=…} (CLDR categories zero one two few many other, exact =0=…, # = the number, forms may hold other placeholders). Positional {0} and named {name} arguments, {{/}} escape. LocaleText[] + LocaleTexts.Get(texts) — for data that carries its own translations (mod info).

UI is localized declaratively: TextComponent has a Localization Key field (LocKey, searchable picker in the inspector, empty = text driven from code) — see ui.md. Per-language fonts: LanguageSettings.Fonts. Examples/Scripts/LocalizationExample.cs is the language-picker recipe.

Localized assets (sprites, audio, any asset per language): a file per language at <Group>/<language>/<Key>.* anywhere under a Localize path (the language folder is a code of the Languages catalog or a language column of the tables). Code generation writes LocAssets.<Group>.<Key> (LocAssetKey, serialized as the key string) and LocalizationTablesGenerated.Assets. Same lookup chain as texts, then any language that has the file. Loaded on demand from the bundle; the previous language's assets leave the bundle cache on a language change.

LocalizationManager.GetAsset<Sprite>(LocAssets.Sprites.Logo); // null + one warning if no file
LocalizationManager.TryGetAsset<AudioClip>(key, out var clip);
LocalizationManager.GetAssetLanguages(key); LocalizationManager.HasAsset(key);
LocalizationManager.RegisterAsset(key, "ru", spriteOrLoader, priority, owner); // runtime / mods
_audio.PlayClip(LocalizationManager.GetAsset<AudioClip>(LocAssets.Voice.Hello), AudioBus.Interface);
[SerializeField, LocAssetType(typeof(Sprite))] private LocAssetKey _icon; // picker filtered by type

Components: LocalizedSprite (on an ImageComponent / Image / SpriteRenderer, SetKey, Refresh, optional native size) and LocalizedAudioSource ([RequireComponent(AudioSource)], swaps the clip, restarts a playing one, Play(); a source with no output group is routed into the mixer group of its Bus, Effects by default). Mods: files under a <language>/ folder in a mod bundle are registered as that language's asset.

No per-language bundles: CORE opens every bundle at boot (AssetBundlesManager.Init) but loads an asset only when asked, so other languages cost download size, not memory.

Editor: Tools/CORE/Localization Editor (CoreLocalizationWindow, also on double click of a table) — grid of keys × languages per table with search and filters (untranslated per language, problems: invalid/duplicate keys, placeholder mismatch vs the fallback language), details panel with multi-line texts and a preview of arguments and plural forms, add/duplicate/rename (rewrites LocKey fields in prefabs/scenes/assets through SerializedObject; same-id AudioKey/LocAssetKey fields are untouched) /delete keys, add/remove languages, create/delete tables, localized-asset pages (drop a file on a cell → copied to <Group>/<lang>/<Key>.ext), an overview (progress per language, generated code up to date, all problems). Changes are in memory until Ctrl+S / focus loss / script reload; Ctrl+Z / Ctrl+Y.

Google Sheets import: configure Assets/COREToolkit/Resources/GoogleSheetsLocalizationConfig.asset (SpreadsheetId, optional Languages filter, AssetFolder inside a Localize path), then run Tools/CORE/Import/Google Sheets Localization — every sheet becomes <AssetFolder>/<Sheet>.csv, the first column is the key; code generation runs afterwards.

Legacy (GameToolkit era, removed in CORE 1.4.0). LocalizedText assets, LocalizationTextGenerated.LocalizeEnums, LocalizationManager.Localize(...), None, AddLocalizations, Localization.Instance.CurrentLanguage still compile and work, marked [Obsolete(LegacyLocalization.Message)]. Never write new code against them. Migration: Tools/CORE/Setup Wizard → Migrations → Localization (also the Setup Wizard check): assets → CSV (CORE's own: only your edits, as an overriding row next to the asset), prefab/scene LocalizeEnums numbers → LocKey (prefab-instance overrides recorded), LocalizedTextBehaviour → TextComponent, migrated assets to the trash, regenerate; keys no table has are reported. Which prefabs and scenes need it is decided by their text (FindLegacyObjectFiles): TextComponent.OnValidate upgrades a loaded component in memory, so the loaded object alone cannot tell. A mod's .csv is a table only with a Key column and at least one language column (catalog code, a language already loaded, or a BCP 47-shaped code); others are skipped with a warning. Replacements: LocalizeEnums.X → LocKeys.<Table>.X; Localize(x).Value → Get(key); SetText(LocalizeEnums) → SetText(LocKey); Localization.Instance.CurrentLanguage = l → LocalizationManager.SetLanguage(code). The shipped LocalizedEnums.cg.cs is frozen at the 1.1.0 members and numbers (LegacyLocalizationManifest.LegacyEnumNames, NONE = 0 … TESTITEMARGS = 40); on generation every member of the current enum that is still wanted keeps its number (a project's enum may differ from CORE's), a 1.1.0 name the enum lacks takes its 1.1.0 number when free, the rest are appended; CORE's keys added since 1.2 get no member. A package update overwrites the file: a project with legacy keys of its own restores its pre-update copy once (the prefabs hold the numbers), then migrates and regenerates. ResourcesLocalizationsLocalizedText.cg.cs ships empty (LegacyLocalizationManifest.ObsoleteFiles); the migration deletes it.

Input key sprites and enums

InputSystem.GenerateCode() reads the action maps of CORE's GameInputActions (the C# wrapper of Resources/InputSystem_Actions.inputactions) and of every .inputactions listed by the InputProjectSettings assets (InputSystem.CollectActionMaps) and writes InputEnums.cg.cs: [Flags] InputGroups (one bit per action map, built by CodeGeneratorHelper.CollectFlagsEnums — existing members keep their bit), InputEnums (<MAP>_<ACTION>), and the switch lookups GetInputGroups, GetActionMapName, GetActionName. A map name used twice across the assets is generated once, from the first asset, with a warning. So adding an action means: edit the game's .inputactions asset → run CORE generation (CORE's own asset also needs Unity to regenerate GameInputActions.cs). The file is CORE's, so a package update overwrites it — run Generate once after updating. Input key icons are InputSystem.GetBindingIcon(input, bindingIndex, InputSizes) (by the current binding) or the legacy ResourcesGenerated.LoadSpriteInput(KeyCode, InputSizes). Usage lives in systems.md.

Checklist when adding an asset

  1. Put the file under a path covered by a BundleData/AssetData in a PlayerResourceSettings asset (yours, under a Resources/ folder).
  2. Confirm Name/Bundle uniqueness and that NameRegex + EnumValues produce the enum shape you want (max 3 groups).
  3. Tell the user to run Tools/CORE/Game Window → Resources → Generate.
  4. Only then reference the generated enum member in code.
  5. If bundles are enabled, the bundle must be rebuilt too.
