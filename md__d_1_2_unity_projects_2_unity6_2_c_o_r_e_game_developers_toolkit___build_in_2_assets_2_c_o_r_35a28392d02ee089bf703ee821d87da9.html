Code style for code built on CORE

Match the CORE codebase. Game code written on top of CORE should be indistinguishable from the CORE file next to it — Assets/COREToolkit/Scripts/** is ~1000 files of reference. Where a project's own CLAUDE.md or style guide says otherwise, the project wins; where everything is silent, follow this file.

General rules

These do not conflict with CORE and should be followed:

  • Member order: nested types → constants → static fields → instance fields → properties → events → constructors → methods → Unity callbacks → interface implementations; within each block public → protected → private, separated by blank lines.
  • #region / #endregion are forbidden — anywhere, for any reason. A region hides size instead of reducing it. Member order plus blank lines give the same structure and cannot be folded away.
  • 500 lines is a hard ceiling for a class — split it. See "Class size" below.
  • No Hungarian notation, no one-letter names except loop indices, no negated booleans (IsLocked, not IsNotLocked).
  • No redundant this.; omit default access modifiers where the surrounding file does.
  • Pattern matching (is Data data, switch expressions, property patterns), string interpolation, nameof, LINQ method syntax.
  • Attributes: one simple attribute inline, several attributes each on their own line, class-level attributes always on their own lines.
  • Async methods that are not Unity callbacks get the Async suffix.

Class size

150 lines is a soft signal to re-check that the class has one job; 500 is a hard split. #region is never the answer. Preference order is extract a collaborator → split into partial files by concern → never just shuffle members to get under the number.

CORE's own precedent for the partial split is GlobalVisual: GlobalVisual.cs (view registry + update loop) + GlobalModVisual.cs (IModSupportVisual), both public partial class GlobalVisual. Generated ResourcesGenerated / ResourcesPlayerGenerated are also partial, one part per AssetData entry.

Note that CORE itself breaks the 500-line rule in six files (SteamInventoryManager.cs 1250, FileManager.cs 819, CustomDropdown.cs 761, CodeGeneratorHelper.cs 663, Helper.cs 645, MathHelper.cs 605). That is not a licence to follow suit — those are framework files you do not edit anyway.

Where the splits go in a VVM project

  • A fat Visual is a design error, not a size problem. A Visual holds inspector references and creates its View. If it has grown, the logic belongs in the View — move it there before reaching for partial.
  • A fat View splits, in order: extract plain collaborator classes and build them with DiContainerRef.Container.Instantiate<T>(new object[] { ... }) so [Zenject.Inject] fields are filled; or break the screen into child Visual/View pairs; or, last, partial by feature.
  • Save logic leaves the View into its own ISaveGameBaseComponent, or use ViewSavedBase<TVisual, TDataSave> which already carries that surface.
  • Config post-processing belongs in the config class's own static Initialize/Validate handlers, not in the consumer.
  • Per-frame work moves to its own IUpdateListiner with its own UpdateOrders slot instead of growing one Update().
  • Editor-only code goes into a partial part or a separate *_Editor_AD type, never behind #if UNITY_EDITOR sprawled through a long runtime class.

Names you must spell "wrong"

CORE ships several typos in public API. Copy them exactly — they are the real identifiers:

IUpdateListiner, IFixedUpdateListiner, IInvokeKeysListiner, InvokeKeysListiner, CashedVisualValue<T>, Extentions, Fillters, ResfreshModsCooldownTime, DefaultAspectRation / AspectRation, RandomeMusic, SetActiveListiner, Complete_Cheat, HazFlag, Equalz, ConverterConfigList (in ConverterListConfigReference.cs).

Performance rules that bite in CORE specifically

  • Do not call GlobalVisual.GetVisual<T>() per frame — it is a LINQ scan. Cache with CashedVisualValue<T> / CachedValue<T>.
  • Prefer GlobalUpdater + IUpdateListiner over adding another MonoBehaviour Update().
  • Use Pool<T> / StaticPool<T> / ListPool<T> for per-frame allocations.
  • SetMaskableWithoutRecursively walks the hierarchy — never in Update.
  • Use GameTime.Time rather than Time.time so pausing works.
