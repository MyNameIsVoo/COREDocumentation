Config System

Namespace CORE.Shared.Configs. Source: Assets/COREToolkit/Scripts/Shared/Configs/. Serialization is Newtonsoft (com.unity.nuget.newtonsoft-json).

Configs are read-only game data authored as .json and loaded once at boot, before anything else runs (ConfigSystem.Init() is step 4 of GameApplication.Awake).

Where files live

Kind Location Read by
Static configs Assets/COREToolkit/Resources/Configs/*.json (any Resources/Configs) FileManager.TryReadJsonsFromResources("Configs", ...)
Dynamic configs {persistentDataPath}/Game/Configs/*.json FileManager.TryReadJsonsFromPath(ConfigSystem.DynamicConfigsDataPath, PersistentDataPath, ...)

The file name is the config's identity — it is matched against your FileName constant.

Two base types

public class MyConfig : ConfigSingle<MyConfig> { } // one object -> MyConfig.Config
public class MyItem : ConfigList<MyItem> { } // keyed array -> MyItem.List / .Dictionary / .Get(id)

The docs call the second one ConfigDictionary<T>; in this codebase it is ConfigList<T>.

ConfigList<T> statics: List, Dictionary, Get(string key), Get(int index), Insert(...), Remove(string key), Remove(List<string> keys). ConfigSingle<T> statics: Config, Insert(...). Both Insert overloads have a variant with a last IList<JsonConverter> converters (may be null; since v1.2) — the config's own json converters, added to the reference resolver for that file.

Every config inherits Config, which gives it [JsonIgnore] public string IdKey (the JSON key, or the file name for singles) and virtual void Validate().

A ConfigList JSON file is an object whose keys become IdKey:

{
"sword_01": { "Damage": 10, "Speed": 1.2 },
"sword_02": { "Damage": 14, "Speed": 0.9 }
}

Registering a config

Registration happens through static events, wired from a [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.BeforeSplashScreen)] method — this must run before ConfigSystem.Init(). ConfigSystem nulls each event after firing it, so a config registered later is simply never loaded.

public class ItemConfig : ConfigList<ItemConfig>
{
public const string FileName = "items" + FileManager.FILE_JSON;
public int Damage;
public float Speed;
[JsonIgnore] public uint Index; // runtime-only
[JsonConverter(typeof(ConverterConfigReference<LootTableConfig>))]
public LootTableConfig LootTable; // reference to another ConfigList entry
[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.BeforeSplashScreen)]
private static void Init()
{
ConfigSystem.InsertConfigs += InsertConfig;
ConfigSystem.InitializeConfigs += Initialize;
ConfigSystem.ValidateConfigs += ValidateConfig;
}
private static void InsertConfig(Dictionary<string, Func<JObject>> jsons, ReferencesConfigResolver context)
{
Insert(jsons.FirstOrDefault(a => a.Key == FileName), context);
}
private static void Initialize() // cross-config wiring, indices, caches
{
for (var i = 0; i < List.Count; i++)
List[i].Index = (uint)i;
}
private static void ValidateConfig() // errors here surface in the Unity console at boot
{
foreach (var item in List)
item.Validate();
}
public override void Validate()
{
base.Validate();
if (Damage < 0)
DebugHelper.LogError($"{nameof(ItemConfig)} [{IdKey}]: Damage must be >= 0");
}
}

The full working pair (single + list) is Examples/Scripts/ConfigsExample.cs.

Events, in firing order

Event Signature Purpose
InsertConfigs Action<Dictionary<string, Func<JObject>>, ReferencesConfigResolver> deserialize your file(s)
InsertDynamicConfigs same same, for the persistent-data dynamic configs
InitializeConfigs Action post-load wiring; all configs exist by now
ValidateConfigs Action integrity checks; log with DebugHelper.LogError

CORE itself inserts GlobalConfig and SettingsConfig (with their fragments) before your handlers run, so those two are always available inside InsertConfigs. (InputConfig no longer exists — input bindings come from the .inputactions asset, see systems.md.)

References between configs

ReferencesConfigResolver (docs call it ConfigReferenceResolver) is Newtonsoft's IReferenceResolver, so a config can hold a real object reference instead of a string id. Use the converters in Configs/Converters/:

Converter For a field of type
ConverterConfigReference<T> T (a single ConfigList<T> entry). Ctor overload (bool weakReference)
ConverterConfigList<TValue> List<TValue> — note: file is ConverterListConfigReference.cs, class is ConverterConfigList
ConverterConfigDictionary<TKey, TValue> Dictionary<TKey, TValue> keyed by a config
ConverterConfigColor Color from a color-library tag

Unresolved references are collected in resolver.Unresolved and reported by context.Validate() at the very end of ConfigSystem.Init(). If a boot log complains about a missing reference, that is where it comes from.

ConfigVisual<T> wraps a visual/resource tag stored in a config so mods and the game resolve it by the same rules; it exposes VisualTag and VisualEnumData and implements IEquatable.

EnumData<T>

EnumData<T> (struct, T : struct, Enum) is CORE's "enum or free string" value, used everywhere a config or a mod may name something that has no generated enum member yet.

public struct EnumData<T> { public T? Enum; public string String; public string Value { get; } }

Value prefers Enum over String. Generated resource loaders take EnumData<T> overloads precisely so mods can pass a string. Construct with new EnumData<T>(SomeEnum.Value, null).

Dynamic (writable) configs

public class LiveTuningConfig : DynamicConfigSingle<LiveTuningConfig>
{
protected override string FileIdentifier => "live_tuning" + FileManager.FILE_JSON;
public float DropRate;
}
await LiveTuningConfig.Config.SaveAsync(); // writes to {persistentDataPath}/Game/Configs/

Register these on ConfigSystem.InsertDynamicConfigs, not InsertConfigs. SaveAsync() throws if a save is already in flight.

Fragments (ConfigFragments)

A package, a DLC or a mod changes a config without editing its file: next to items.json (any Resources/Configs) it ships items.<part>.json. Applied after the base file, by file name, ordinal: objects merge recursively, scalars and arrays replace, "Name+": [...] appends to the array Name, { "$remove": true } removes the entry or property. An entry that only appends is a patch: it waits for its entry and is dropped when no file declares it (data for a package that may not be installed). Use it instead of Insert:

private static void InsertConfig(Dictionary<string, Func<JObject>> jsons, ReferencesConfigResolver context) =>
ConfigFragments.InsertList<ItemConfig>(jsons, FileName, context); // InsertSingle<T> for a ConfigSingle

ConfigFragments.Merge(target, patch), IsPatchOnly, IsRemoval, Collect serve tools that rebuild the merged view. global.json and settings.json are loaded this way; Settings.DefaultSettings is a copy of the merged SettingsConfig.Config, so a settings.<part>.json fragment also sets what a new player starts with and what Reset restores.

Config Editor (editor)

Tools/CORE/Config Editor (CORE.Editor.Configs.CoreConfigEditorWindow, Scripts/Editor/Game/ConfigEditor/): every ConfigList<T> / ConfigSingle<T> with a const string FileName, in any assembly, edited as entries with fields, merged from all its files and written back into the file each value belongs to. Sidebar groups: one per package (KitModule of the class's assembly, else of its folder), the game's own last — packages never mix. A package's menu opens its group: CoreConfigEditorWindow.OpenModule("inventory"); an entry: CoreConfigEditorWindow.Open(typeof(ItemConfig), "sword").

Runtime hints the editor reads (namespace CORE.Shared.Configs, no effect at runtime):

Attribute On Editor shows
[ConfigReference(typeof(X)) { Prefix = "…" }] string (or string[]) ids of config X, checked
[ConfigEnum(typeof(E))] string members of E, free text allowed
[ConfigChoices("source")] string (or string[]) names of a ConfigChoiceSource: core.bundle, core.input, core.language, a package's own (<module>.<name>)
[ConfigColor] string #RRGGBB colour picker
[LocalizationKey] string a key of the CSV localization tables with its text; a LocKey field needs no attribute (json: the key string)

Extending it from a package's editor assembly (references Game_Editor_AD): subclass ConfigEditorExtension (found by itself) — Validate(workspace, issues), CreateEntryHeader(context), CreateTemplate(family, id), GetCreateAction(family) (wizard button), PolymorphicFamilies (ConfigPolymorphicFamily(baseType, discriminator, idOf, unique) — json naming its class in a field), GetFamilyGlyph, GetEntryIcon, GetEntryCaption, GetFieldAttention, ClearCaches. A list of names: subclass ConfigChoiceSource (Id, Title, GetChoices); a list of another config's ids: ConfigIdChoiceSource (RootType). Labels: <module>.configs.families.<stem>, <module>.configs.fields.<Class>.<Field> (+Tip), <module>.configs.types.<id> in the package's editor texts. Team settings (json line width, muted checks) are in CoreEditorSettings, personal ones (auto check, delay, confirm delete) in CoreEditorUserSettings — Settings → Config files / Config editor.

Overrides of CORE's configs: CORE's own files (ConfigPackage.IsCore — global.json, settings.json, audio.json) are replaced by a package update, so never keep the game's values in them — put them in a fragment of the game, global.game.json in its Resources/Configs. The header's Override file button creates one at a path the user picks (must be in a Resources/Configs outside CORE, named <stem>.<part>.json, unique) and makes it the entry's target. Saving a changed CORE file asks to move the changes into the game's fragment (the target picked, else the game's last file of the config, else a new file at a picked path) or to write CORE's file anyway. API: ConfigOverride.Diff(before, after) (the fragment turning one into the other, $remove for gone properties), Apply(fragment, patch), Check(workspace, family, path) → ConfigOverridePathError; ConfigWorkspace.GetOrCreateOverride(family, path), MoveIntoOverride(source, target) (one undo step).

Saving: a file counts as changed when it differs from the file on disk, so undo works across a save (stepping back past Save marks the file changed again); a rename, a delete or an applied draft is one undo step even across several files (ConfigWorkspace.BeginGroup / EndGroup). Files changed on disk while the window is open (git, the Audio Editor) are re-read on focus when unchanged in the editor; for a file with unsaved changes Save asks Keep mine / Take from disk. Each file is written through a temporary file; a failed write is reported and the file stays unsaved (ConfigWorkspace.SaveAll returns the failures). Two config files of one name in different Resources/Configs folders: the first one found is loaded, the other is logged (ConfigFileNames.ReportDuplicate) and ignored — the Problems page reports it (core.configs.issues.duplicateFile); global, settings and audio are CORE's names.

Gotchas

  • ConfigSystem.Init() bails out entirely if Resources/Configs cannot be read — no configs, no error other than the missing data.
  • IdKey is [JsonIgnore]; do not put an "IdKey" field in the JSON.
  • Registering from anything later than BeforeSplashScreen (e.g. a MonoBehaviour Awake) is too late in most scenes.
  • ConfigSystem.Loading is true during load; LoadConfig(Action) exists to run extra deserialization under that flag (mods use it).
